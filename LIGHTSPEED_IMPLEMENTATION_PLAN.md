# Implementation plan: ACME → Praxis → OpenShift Lightspeed → OpenShift MCP

**Purpose:** a phase-by-phase handoff for implementation agents. This document is an execution plan, **not** an assertion that any phase has been completed. The requirements, security reasoning, and upstream source links live in [LIGHTSPEED_MIGRATION_PLAN.md](LIGHTSPEED_MIGRATION_PLAN.md); read it first. The requested target is a **greenfield standalone deployment**, not an in-place update of a cluster running the former RCA agent. Its source/chart and standalone application have been removed. Implement the **standalone** variant only. Do not change `hub`/`group-one` deployments.

## Rules and shared contracts

- Do not deploy or restore the former RCA agent as a fallback. This plan is not an in-place migration procedure for clusters already running it. Keep the new OLS/Praxis/ACME path disabled until all security and runtime gates pass. Do not delete or overwrite unrelated/untracked work. Do not commit credentials, generated tokens, kubeconfigs, or live Secret values. Use the pattern's Vault → ESO convention; keep human login/break-glass working.
- The request chain is `ACME --Token A + X-OLS-Cluster--> Praxis --same Token A + header--> selected OLS --Token B--> its operator-managed MCP --Token B--> that cluster's API`. Token A is ACME's SPIFFE-federated Keycloak token. Token B is a fresh, per-request Keycloak RFC 8693 exchange with `aud=openshift-mcp`, `sub` inherited from A, `azp=lightspeed-mcp`, and the expected group. Never replace B with either pod's ServiceAccount token or pass A to MCP. ACME's LiteLLM coordinator uses `openai/gpt-6-luna`; Lightspeed's incident-analysis model remains the configured Vertex Gemini model, not ACME's coordinator model.
- Target selection is **not** authorization: ACME validates a cluster API URL against a configured allow-list, sends a derived ID in `X-OLS-Cluster`; Praxis checks the Keycloak caller **and** the allow-listed ID, then reverse-proxies only to the static backend registered for that ID. OpenShift RBAC on the selected cluster authorizes MCP tool calls. No dynamic upstream URL, silent default cluster, HTTP redirect carrying tokens, or cross-cluster round-robin.
- One target for now: the candidate API URL is `https://api.bm-cluster.e2e.bos.redhat.com:6443` and the ID is `api-bm-cluster-e2e-bos-redhat-com-6443`. **Check `oc whoami --show-server` first.** Treat both as placeholders until confirmed. Standardize one header spelling (`X-OLS-Cluster`), one canonicalization/ID algorithm and one registry schema. The header's value is an ID, not a URL. ACME and Praxis must render their allow-lists from the same GitOps values, not independently maintained lists.
- Candidate shared registry shape (finalize in Phase 0; the `upstreamHost` and SNI are examples, not checked deployments):

  ```yaml
  global:
      olsClusters:
        api-bm-cluster-e2e-bos-redhat-com-6443:
          apiURL: https://api.bm-cluster.e2e.bos.redhat.com:6443
          upstreamHost: lightspeed-app-server.openshift-lightspeed.svc.cluster.local
          upstreamPort: 8443
          upstreamSNI: lightspeed-app-server.openshift-lightspeed.svc
        # Future target example only; fake hostname, disabled by comment.
        # Do not enable until its OLS/MCP, TLS, Keycloak audiences, RBAC and
        # cross-cluster network path are separately configured and verified.
        # example-second-cluster:
        #   apiURL: https://api.example-second.invalid:6443
        #   upstreamHost: lightspeed-app-server.example-second.invalid
        #   upstreamPort: 443
        #   upstreamSNI: lightspeed.example-second.invalid
  ```

  ACME receives only `apiURL` + map key (ID); Praxis receives only map key + static upstream/TLS configuration. Do not let ACME obtain arbitrary upstream addresses or let Praxis route to `apiURL`. Store the registry in Pattern values and supply chart stubs for standalone Helm rendering.
- Existing ACME browser access is not human-authenticated; Keycloak identifies **the ACME workload**, not the person entering the URL. The registry and OCP group grants therefore bound what *any* ACME user can request. If per-human cluster rights are required, treat browser authentication and user-subject propagation as a separate blocking design decision; a target header is not a user-authorization mechanism.
- ACME's current UI is one-shot. The first implementation accepts inbound `message/send` only and requires the target URL in that message; it rejects inbound task polling/cancel rather than risk losing cluster affinity. Supporting inbound task methods later requires durable, authenticated task/context-ID → cluster-ID ownership and mismatch tests. Separately, ACME must attach the invocation-scoped header to every *outbound* A2A POST its downstream `RemoteA2aAgent` makes.
- Run tests after each phase. A phase's listed evidence is its handoff artifact; do not claim completion from YAML rendering alone when it calls for a real cluster. Record the pinned upstream revisions and actual OLM/operator/MCP image versions tested. Do not change security controls to make a test pass.

## Release and file ownership map

| Workstream | Primary files | Contract to other workstreams |
| --- | --- | --- |
| Service source/A2A | `vendor/lightspeed-service/` (new), image build notes | Produces a pinned image with an authenticated A2A endpoint; its agent card advertises the Praxis HTTPS origin; receives validated target ID; sends only exchanged token to the built-in `openshift` MCP client. |
| Operator/MCP | OpenShift Lightspeed Operator deployment/packaging changes **only if required**, `charts/all/openshift-lightspeed-config/` (new) | Supplies the service image override, operator-generated MCP auth/tool hardening, TLS/CA, SPIFFE mount and compatible ingress restriction. Must not overwrite the operator's reconciled operands from another Argo application. |
| Keycloak/OCP RBAC | `charts/all/keycloak-oidc/`, `values-secret.yaml.template` | Fresh-realm client/audience/group configuration for ACME and Lightspeed; uses a PostSync reconciler for Lightspeed client/group setup. Keep native OIDC/break-glass and human AgenticRun permissions separate. |
| ACME | `agents/acme_agent/src/acme_agent/`, `agents/acme_agent/tests/`, `charts/all/acme-agent/` | Implements prompt plus enforced URL selection and invocation-scoped header on every A2A RPC; card discovery must work without a target. |
| Praxis | `charts/all/praxis-proxy/` | Routes by exact allow-listed header to fixed HTTPS upstream; Keycloak enforcement still precedes routing; missing/unknown header cannot reach OLS. |
| Pattern orchestration | `variants/standalone/values-standalone.yaml`, documentation | Wires inert downstream operator/OLSConfig/Praxis chart applications for greenfield; do not enable them before deployment inputs and CRD readiness are verified. |

Coordinate edits to `variants/standalone/values-standalone.yaml` and `charts/all/keycloak-oidc/` through one integrator; avoid competing changes to these shared files. Workstreams can be developed independently once the Phase 0 interfaces are frozen, but **no production cutover** is parallel with security validation.

## Phase 3 — Keycloak realm migration and scoped OpenShift permissions

**Depends on:** actual SA, issuer/audience and cluster ID from Phases 0/2. **Outputs:** fresh-realm chart configuration and tested idempotent Lightspeed client/group reconciliation. Do not alter cluster-wide human OIDC/break-glass behavior as part of workload cleanup.

1. For a fresh realm, configure the confidential SPIFFE-federated `lightspeed-mcp` client bound to the actual OLS SA, standard exchange, the real `openshift-mcp` audience mapper and `groups` mapper. Give ACME's client the `lightspeed-a2a` inbound audience and **real** `lightspeed-mcp` client audience. The greenfield group is `acme-agent-lightspeed`; ensure ACME's service account is a member and both relevant clients emit groups. No RCA client/audience mapper is retained. Use the realm issuer as the SPIFFE assertion audience; omit `client_id` from federated token requests.
2. `KeycloakRealmImport` is one-shot. Use the dedicated Lightspeed PostSync reconciler on a fresh realm to ensure its client, mappers and ACME membership, then test repeat-sync idempotency. This does not remove old objects from an already-imported realm; existing clusters require a separate reviewed migration/cleanup and are outside this greenfield plan. Keep admin credentials only in the existing Secret mechanism; protect console/CLI OIDC and break-glass throughout.
3. Keep `openshift-mcp` in `openshiftOIDC.extraAudiences`; retain `sub` → `keycloak:` username and `groups` → `keycloak:` group mapping, issuer URL and synced CA. Add *only* reviewed namespace-scoped read Roles/RoleBindings for `keycloak:acme-agent-lightspeed`; do not reuse human AgenticRun permissions for MCP. Review pods/logs, events, metrics and cluster-scoped tools individually for sensitive data. Keep the separate AgenticRun admission policy for its human workflow.
4. Verify Token A and Token B against a live Keycloak realm (print **claims only**): A has both required audiences; B has same `sub`, `azp=lightspeed-mcp`, `aud=openshift-mcp`, expected group. Verify a real API-server TokenReview/harmless read yields the prefixed username/group and intended namespace rights; deny a second namespace and writes. Impersonation is only a pre-check, not a substitute for a real-token test.

**Exit evidence:** rendered Keycloak/OIDC/RBAC diff; repeatable realm migration; redacted claim matrix; positive/negative API-server authorization results. If B lacks `groups`, **stop** and correct the mapper/membership before letting tools run.

## Phase 4 — Lightspeed A2A endpoint and per-request identity

**Depends on:** Phase 0 A2A contract, Phase 1 source, Phase 3 identity contract. **Output:** tested changes under `vendor/lightspeed-service/`; do not bypass the usual OLS query/tool pipeline.

1. Register A2A routes/card in the pinned service. Serve the public, cluster-neutral `/.well-known/agent-card.json` card with **Praxis HTTPS URL** as advertised RPC endpoint. Implement the methods ACME actually uses (`message/send`, task lookup, terminal/error propagation; prove streaming/cancel before claiming support) and a safe readiness endpoint.
2. At the A2A boundary independently validate Token A against Keycloak discovery/JWKS (verified CA, signature/RS256, exact issuer, `lightspeed-a2a` audience, expiry and `azp=acme-agent`), reject missing/unknown `X-OLS-Cluster`, and compare the header with this OLS instance's configured cluster ID. Never trust forwarded user/cluster identity from an unauthenticated HTTP header. Keep stock REST authentication on `k8s` TokenReview/SAR, with no ACME `/ols-access` permission as a shortcut.
3. Fetch a fresh SPIFFE JWT-SVID for the OLS workload and perform Keycloak RFC 8693 exchange for each caller request. Preserve caller `sub`, verify B's issuer/audience/expected group before calling tools, then feed **only B** into OLS's built-in `mcp_servers` token-resolution path for this invocation. Prevent client-provided `MCP-HEADERS` from replacing it. Fail closed on unavailable exchange, MCP or absent tools; don't return a fabricated successful diagnosis. Avoid token state in global variables, persisted tasks, logs or transcript text; re-exchange securely if an async task outlives a token.
4. Scope task/context storage to authenticated caller and cluster ID; ensure polls/cancellations cannot read a different caller's data or switch clusters. Add unit/integration tests for malformed/missing/expired/wrong issuer/audience/client, JWKS/CA rotation, exchange failures, group mismatch, concurrent independent callers/targets, card HTTPS URL, downstream failure, REST regression and no token leakage.

**Exit evidence:** service tests, ADK-compatible A2A/card exchange against the modified service, MCP request capture showing **B, never A**, and a non-sensitive Gemini/tool response with auth still enabled.

## Phase 5 — ACME target enforcement and A2A header transport

**Depends on:** Phase 0 registry/card contract; can be developed in parallel with Phase 4. **Output:** changes in `agents/acme_agent/`, its tests and chart.

1. Extend the root-agent instruction to ask for an explicit OpenShift API URL and withhold delegation otherwise; implement a **server-side** validator before remote dispatch. Canonicalize HTTPS URL, reject credentials/paths/query/fragment, look up the single allowed URL and return the registered ID. The browser UI (`agents/acme_agent/src/acme_agent/ui.py`) is currently one-shot and does not persist conversation/context; require the URL on **every** message until stateful clarification is implemented. An optional required UI field does **not** replace A2A server-side enforcement for other clients.
2. Configure the same registered URL/ID in `charts/all/acme-agent/values.yaml` and its Deployment as a non-secret setting derived from the shared registry. Keep `a2a.remoteAgents[0].endpoint` pointed at the single Praxis HTTPS Route, not at per-cluster OLS Services. Keep ACME Keycloak/SPIFFE and LiteLLM configurations separate from the new OLS Gemini provider.
3. Add `X-OLS-Cluster: <registered-id>` to the shared client's **outgoing authenticated A2A RPC** in an invocation/task-scoped way. Do not set a global header or send user text as a destination. Keep card discovery public and independent of target selection. Check every follow-up method; adapt the ADK transport if its event-hook/context lifecycle loses the selection.
4. Unit-test URL/ID canonicalization and collision/length handling, absent/unknown/ambiguous URLs, prompt enforcement, card discovery, no downstream call on rejection, and two interleaved requests with different simulated target IDs (no header/token cross-talk). Verify unsupported inbound task polling/cancel is rejected before ADK. If implementing inbound task support rather than rejecting it, persist and authenticate task/context ownership and test that follow-up requests cannot switch targets.

**Exit evidence:** exact header on each authorized RPC, no header-derived outbound URL, passing ACME tests and verified UI behavior for clarification without state.

If a greenfield gateway validation fails, disable it rather than falling back to the stock image, which lacks the selector guard. Review the pre-release risk of Core v0.7.2 and record approval before publication.

3. ## Phase 8 — Greenfield installation and observation

**Depends on:** approved Phase 7 exit gate, published immutable images/catalog, verified cluster values, and working break-glass access. **Output:** one active A2A route and a validated greenfield deployment.

1. After the versioned operator is ready and the CRD gate passes, enable OLSConfig with the verified SPIFFE subject, CA, reviewed MCP RBAC, Vertex credentials and immutable service image. Enable Praxis only with the published guard image, verified static cluster registry and public HTTPS origin; then configure ACME to that same Praxis origin and turn on server-side cluster selection. Do not enable a step with an illustrative hostname or local-only image digest.
2. Observe readiness, Praxis denies, OLS/MCP errors, RBAC denies and model/tool behavior. If validation fails, disable the new ACME delegation/Praxis route and OLS A2A/introspection together; do not introduce an RCA fallback. Keep cluster-admin break-glass access available. Do not reset user changes or weaken authentication to troubleshoot.
3. The RCA agent source/chart and its standalone app are retired for greenfield installs. Keep the separate agentic operator/CRDs and its human AgenticRun RBAC/VAP unless a separate dependency audit proves they are unused. Keep Vault/ESO, ACME LiteLLM, Keycloak native OIDC, RHOAI and unrelated MAO intact.

**Final handoff:** list files changed, exact pinned revisions/images (Praxis Core release, Praxis AI source/version, OCI digest), chart/test results, redacted live validation matrix, known limitations including the Core pre-release status, disable/rollback procedure, and owner/steps for registering a second cluster (its own OLS/MCP, Keycloak federation/audience, API-server OIDC/RBAC, verified TLS path and registry entry). No agent should call this complete solely because Argo reports Synced.

| Request/scenario | Expected result |
| --- | --- |
| Missing or unregistered cluster URL in ACME | Ask for explicit API URL or reject; **no downstream RPC**. |
| Valid ACME token, absent/unknown/malformed `X-OLS-Cluster` | Praxis rejects without forwarding; no default backend. |
| Valid header with absent/invalid/wrong-audience Keycloak Token A | Praxis and OLS each deny in independent tests. |
| Valid token/header targeting the wrong OLS backend | Backend rejects its mismatched configured cluster ID; no cross-cluster MCP call. |
| MCP call without a bearer; invalid or expired Token B | MCP rejects (or API denies invalid B); **no pod-SA fallback**. |
| Token B without expected group, or API read outside authorized namespace | OCP RBAC denies; no elevation via header, MCP tools or other cluster. |
| Disallowed write/Secret/RBAC MCP tools | Tools absent or Kubernetes denies; do not rely on model prompt alone. |
| Two ACME `message/send` invocations interleaved | Header, token, request context and selected backend remain isolated per request/cluster. Unsupported inbound ACME task polls/cancel are rejected; if later supported, require durable task ownership and test that target affinity. |
| OLM/operator reconciliation, CA rotation or upgrade | Service image, MCP hardening and trust survive; otherwise block upgrade/cutover. |
