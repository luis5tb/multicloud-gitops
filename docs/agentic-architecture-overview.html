Agentic pattern: how the components fit together

ACME asks MAS; MAS delegates cluster investigations to the lightspeed-hub over A2A, through the Praxis hub gateway. Analysis and Verification use the read-only Praxis spoke gateway; Execution uses a separate gateway only after the approval checkpoint. Keycloak (realm rca) issues and exchanges each hop's token. The execution split is implemented but not live-verified and remains disabled in standalone. The step-by-step token walkthrough is in agentic-e2e-token-flow.html.

Token A · caller (acme-agent) Token H · run creation Token R · run credential Token U · spoke reads Token R_exec · approved execution credential Token U_exec · execution gateway token Keycloak token endpoint identity / LLM / control Blue-bordered boxes: Praxis instances

Token paths: four live, two implemented

The read-only path (A, H, R, U) is live-verified. The separate execution tokens R_exec and U_exec are implemented but not live-verified and remain disabled in standalone. Rule: each token's audience is the client that exchanges or consumes it next, so every exchange asks for one audience, and Keycloak's "exchanger must be in the subject token's aud" holds by construction. Exchanges preserve sub; for the current ACME client-credentials flow, this is ACME's service-account identity, not the person using its UI.

Components

ACME agent

Chat agent (ns acme-agent). Answers Red Hat questions by delegating to MAS.

  • Keycloak client acme-agent, authenticated with its SPIFFE JWT-SVID (no static secret)
  • Calls MAS A2A with Token A
  • LLM through LiteLLM

MAS (mao)

Multi-agent orchestrator. The A2A endpoint is the pattern's front door.

  • MAS A2A validates A and seals it (Fernet) into the Temporal task
  • Hub node uses hitl_mode: ask; approval continues the paused task
  • mas-worker routes to the remote agent "Hub Cluster Investigator" and forwards A
  • Gemini on Vertex AI

Praxis hub gateway

praxis-proxy Deployment and Route (ns praxis-proxy).

  • Validates A (Keycloak, or Red Hat SSO as alt issuer), azp allow-list
  • RFC 8693 delegation as mas-a2a: A → H
  • Routes A2A to the adapter; serves the adapter's agent card publicly

lightspeed-hub A2A adapter

Translates A2A tasks into AgenticRuns (repo lightspeed-hub).

  • Creates the three-stage AgenticRun with H (the caller's identity); Execution is manual approval
  • Exchanges H → R; after approval also exchanges H → R_exec and patches approval as caller
  • Watches runs with its own ServiceAccount; removes the execution key after the stage

lightspeed-agentic-operator

Runs the investigation (repo lightspeed-agentic-operator, gateway credential mode).

  • Agent default, LLMProvider vertex, ApprovalPolicy cluster
  • Analysis/Verification use read gateway + R; approved Execution uses exec gateway + R_exec
  • No spoke ServiceAccount, no spoke-management kubeconfig

Praxis spoke gateway

One read gateway per spoke: praxis-spoke-<id> (here praxis-spoke-hub); the optional execution gateway has a distinct app-name selector.

  • Read validates R and exchanges R → U per call
  • Execution uses R_exec → U_exec; its NetworkPolicy peer requires agentic.openshift.io/step=execution; read selector is unchanged
  • Fixed upstream: the spoke API, TLS verified; IPv4-only DNS sidecar

Keycloak (RHBK)

Realm rca, imported by charts/all/keycloak-oidc.

  • Issues A; performs the three exchanges
  • Client roles projected into groups per audience
  • Issuer for OpenShift Native OIDC on the kube APIs

Kube APIs

OpenShift Native OIDC maps sub → keycloak:<sub>, groups → keycloak:<group>.

  • Hub: H's creator group creates runs; caller's approver group patches approval
  • Spoke: U gets reader RBAC; U_exec gets writer RoleBindings only in allowed namespaces. Workloads there can use any ServiceAccount and mount Secrets; see the chart README.
  • A and R are rejected at kube APIs; execution is not live-verified

Vault, ESO, Red Hat SSO, Vertex

Supporting services.

  • Vault + External Secrets deliver every client secret and the Vertex credentials
  • Red Hat SSO: alternative issuer (aud api.ask_red_hat) for SSO callers and Ask Red Hat
  • Vertex AI: one credential and model for MAS and the sandbox
