One request, end to end · implementation walkthrough

“Investigate the issue in namespace payments on cluster west.”

Follow MAS’s A2A request into an AgenticRun, watch analysis turn into an approval question, and follow the human’s answer back into execution and automatic verification.

Code walkthrough, not a live execution. This describes the local remediation implementation reviewed in the cross-repository review. Payloads and outcomes are illustrative; execution still has rollout blockers. Nothing on this page calls a cluster.

Example names only. The proposal buttons in step 4 change the downstream story.

The short version: A2A request → run with all three steps → analysis result → input-required → same-task decision → approval object update → execute, then verify → A2A result.

1

MAS → Hub A2A adapter → Kubernetes API

The question becomes a run, not an analysis-only job

MAS invokes message/stream. The adapter joins the message’s TextParts into spec.request, resolves the target cluster, and CREATEs an AgenticRun using the caller’s Hub credential (H).

A2A request arriving at the Hub

Hub-leg HTTP header: X-Hub-Cluster: west. Authorization headers are omitted throughout.

Created AgenticRun · abbreviated metadata

hub-runs and default stand in for the configured run namespace and agent. a2a-example is a shortened run-name alias.

  • Namespace X is request text. It is not extracted into a dedicated scope field and is not the run’s metadata.namespace.
  • Cluster Y is structured routing. In this example the routed X-Hub-Cluster header supplies spec.targetCluster; mentioning a cluster in prose does not select it.
  • All three agent refs already exist. The approval policy is Analysis = Automatic, Execution = Manual, Verification = Automatic. Execution being configured does not approve it.
IDs, real run name, and initial credential setup

The initial request below uses explicit illustrative IDs. If omitted, the Hub allocates task/context IDs and returns them in its initial kind: "task" event; MAS must retain the Hub IDs, not substitute an outer MAS task ID.

The real run name for hub-context-17 / hub-task-42 is a2a-969b461702bff4852960fb27b7c5c991d82c4c33: "a2a-" + first40hex(SHA-256(contextId + NUL + taskId)). Every example uses a2a-example instead.

After the run is created as H, the adapter exchanges the incoming credential for a scoped run credential (R) and writes its run-token Secret as the adapter ServiceAccount. The examples omit tokens, resource versions, timestamps, UIDs, and unrelated metadata. The header route shown here is not the adapter’s only accepted structured target input.

2

Operator → analysis sandbox → Result + run status → adapter → MAS

Automatic analysis publishes proposals and advances the run

The operator observes the new run, creates its same-name AgenticRunApproval with the automatic stages, and launches an analysis sandbox. The sandbox creates an AnalysisResult and writes its status on the Hub API. When the Pod completes, the operator reads the result’s Completed=True, appends a successful result reference, and updates the run’s conditions.

AnalysisResult · relevant fields

Diagnosis, remediation/verification plans, RBAC, and other result fields are omitted here; this is not a runnable remediation manifest.

AgenticRun · status after analysis

Phases are derived from conditions. While Analyzed=Unknown, the phase is Analyzing → A2A working. With Analyzed=True and execution not yet started, it is Proposed → input-required.

How the change reaches MAS: the adapter’s shared Kubernetes informers watch runs, Results, and approvals. A Result event resolves the parent through spec.agenticRunName; an approval uses its same-name run. The adapter re-projects that run into its task store; Store.PutTask signals streamUpdates, which emits A2A events on MAS’s open SSE stream. MAS does not open its own Kubernetes watch.

3

Hub adapter → MAS · current SSE attachment ends here

The completed analysis becomes an approval question

The adapter reads the latest successful analysis referenced by the run. approvalDetail builds a status message with two parts: readable text and a structured approvalRequest. Its options preserve analysis order: human proposal 1 has index 0; proposal 2 has index 1.

A2A status event returned to MAS

Shown as the SSE JSON-RPC result body, not the surrounding data: envelope. Generated message IDs and timestamps are simplified.

Before this status event, the stream emits the newly available analysis as an artifact-update: a TextPart summary plus a DataPart containing the AnalysisResult.status payload. The approval question itself lives in status.message, not in a standalone A2A message response.

final: true ends this stream, not this task. The task is input-required, remains resumable, and is waiting for a new message on the same Hub task/context.

5

Hub adapter → Kubernetes API · UPDATE AgenticRunApproval as H

The decision changes the approval, not the run’s step spec

The adapter reads the approval as its ServiceAccount, adds the Execution stage decision, and performs a full-object UPDATE using the caller’s H credential. The object has the same name and namespace as the run. The following are relevant-field excerpts, not a literal merge patch.

Before · seeded by the operator

Automatic Analysis/Verification entries normally have no explicit decision. There is no Execution decision yet.

After · proposal 2 approved

The trigger: the operator owns/watches AgenticRunApproval. Its update queues the parent run for reconciliation. The adapter also watches the approval so the A2A projection can leave the old approval checkpoint while the operator catches up.

Credential preparation and why “approval update” is not the whole transaction

On the configured remote-cluster execution path, before updating an Approved Execution decision the adapter records the approved-analysis identity on the run as its ServiceAccount, exchanges credentials for R and the execution credential (R_exec), and writes both Secret keys as its ServiceAccount. Only then does it UPDATE the approval as H. Rejection does not mint R_exec.

That ordering is the current implementation, not a guarantee of atomicity or proof that the security findings are fixed. The review’s trust boundaries and rollout gates remain applicable. There is no Secret informer in the adapter’s event path.

6

Approval watch → operator reconciliation → sandbox work

Approval unlocks execution; verification needs no second answer

  1. Execution: handleExecution checks approval, trims AnalysisResult.status.options to the selected option, sets Executed=Unknown, and launches an execution sandbox. Its input includes the selected remediation, rather than the whole original proposal list.
  2. Execution completes: the sandbox writes an ExecutionResult; Pod completion leads the operator to record a successful result ref and Executed=True. The derived phase becomes Verifying.
  3. Verification starts automatically: the existing automatic Verification approval allows the operator to launch verification using the selected option plus execution output. Verified=Unknown means work is in progress.
  4. Verification succeeds: a successful VerificationResult is referenced and Verified=True makes the derived run phase Completed.

Rejected means no remediation

The operator sees Execution / Denied, marks the run Denied, and launches neither execution nor verification. The analysis remains available; a “completed” A2A answer in this branch means the investigation finished, not that the proposed fix was performed.

Run condition / phaseA2A projectionWhat MAS can observe

Approval stops the stale input-required projection before the run’s conditions necessarily change. Analyzing, Executing, Verifying, and Escalating all map to working. The stream emits a new status event only when the A2A state changes, not for every operator phase; new Result IDs produce artifact events.

Final status event

Both the current stream and the task are finished now. The successful text comes from a run condition, not the verification summary. Intermediate snapshots can coalesce; these examples do not promise an exact event count.

What if there is nothing to fix, or verification fails?

If analysis returns actionRequired: "False", the operator’s NoActionRequired path completes the run after analysis: no execution or verification is launched, even though all three refs were configured. A negative verification can lead to escalation rather than the successful path shown here.

The adapter projects each step’s newest successful Result reference as an artifact. A new attachment can replay existing artifacts, so MAS should use their stable IDs, not treat each replay as a new remediation.

Keep the two responsibilities separate: the adapter translates A2A ↔ Kubernetes objects/events. The operator decides when to run each sandbox from the run, approval, and policy. MAS receives the approval question and sends the human’s answer back on the same Hub task.
