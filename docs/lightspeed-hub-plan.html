multicloud-gitops · rca-mao-praxis-hub · as implemented

ACME → MAS → hub sandbox → spoke API

OpenShift Lightspeed is replaced by lightspeed-hub and a purpose-built A2A adapter. The caller's token is exchanged three times on the way — at the Praxis hub gateway (A → H), in the adapter (H → R) and at a per-spoke Praxis gateway (R → U) — so the hub creates the run as the caller and the spoke applies the caller's audience-scoped RBAC. Phase 3 (removing the standing spoke kubeconfig on the registration side) is not started.

The implemented flow, end to end

Two Praxis policy checkpoints on the hub: the hub gateway before run creation, and one spoke gateway per spoke before every call to that spoke's API. Each exchange mints a token for exactly the next hop.

How to read the implemented flow

Each token's audience is the client that exchanges or consumes it next. Keycloak 26 only lets a client exchange a token that names it in aud, the exchange audience must be an existing client, and the pinned Praxis delegate() asks for a single audience. So A names mas-a2a, H names lightspeed-hub-a2a, R names praxis-spoke-gateway.

A chain, not the planned fan-out. The plan had two independent exchanges from A (A → H and A → U) with A parked for the run. Parking A failed live: A lives 5 minutes and investigations died. Now the hub gateway exchanges A, so the adapter never sees it; the adapter derives the run credential R from H; R lasts 1800 s because an exchanged token takes the exchanging client's lifespan, and it is useless anywhere but the spoke gateway (401 at every kube API).

Groups are audience-scoped roles. Each exchanger's client-role mapper projects a role of the target audience into groups: H carries lightspeed-hub-a2a:agenticrun-creator, U carries praxis-spoke-<id>:reader. Kubernetes binds groups, so run creation and spoke reads get different permissions for the same sub.

Identity: Token A is still ACME's own principal (client credentials with a SPIFFE assertion), not a signed-in human. All four tokens carry that same sub; azp becomes the exchanging client at each hop.

How a new sandbox is routed through the spoke gateway

The hub API stores the run, the operator creates the pod, and a generated kubeconfig selects the data path. Praxis does not need to discover each new sandbox. This is lightspeed-agentic-operator's gateway credential mode.

1 · One gateway per spoke, not per run

Each spoke gets a stable internal HTTPS Service backed by its own Praxis Deployment (praxis-spoke-<id>.praxis-proxy.svc:8443, chart praxis-proxy, spokeGateways.<id>). It forwards to one fixed spoke API and exchanges for one spoke audience. Many short-lived sandboxes reuse it; neither the model nor a header supplies the upstream.

2 · The sandbox kubeconfig points at that Service

The operator writes the kubeconfig below (captured from a live sandbox) and sets KUBECONFIG. kubectl then reaches the gateway instead of the spoke API, with no command rewriting or interception.

apiVersion: v1
kind: Config
clusters:
  - name: spoke-via-gateway
    cluster:
      server: https://praxis-spoke-hub.praxis-proxy.svc.cluster.local:8443
      certificate-authority: /var/run/secrets/praxis-gateway/ca.crt
users:
  - name: requester
    user:
      tokenFile: /var/run/secrets/run-identity/token-a   # the run token R
contexts:
  - name: spoke
    context:
      cluster: spoke-via-gateway
      user: requester
current-context: spoke

3 · Two TLS legs

The sandbox trusts the OpenShift service-serving CA (copied into the praxis-gateway Secret by the chart's CA-sync bridge). The gateway validates R (signature, issuer, audience praxis-spoke-gateway, azp in spokeGatewayConfig.allowedCallers), exchanges it for U as client praxis-spoke-gateway, replaces Authorization, strips routing headers and forwards to the fixed spoke API, verifying that API's own CA and SNI. Responses are capped at 32 MiB.

4 · Containment

The gateway's NetworkPolicy admits only the sandbox namespace (lightspeed-hub) and allows egress to DNS (ports 53 and 5353), Keycloak and the spoke API port. The gateway pod runs an IPv4-only DNS sidecar on this cluster. Default-deny egress for the sandbox itself is still a hardening item.

5 · Renewal without changing the endpoint

The adapter rewrites R in the same Secret; the mount has no subPath and kubectl reads tokenFile per request, so the new R is picked up in place.

What was verified

Kube API pass-through on the pinned Praxis (ghcr.io/praxis-proxy/ai:0.4.1) works for arbitrary paths, watch streaming and websocket upgrades; kubectl exec over SPDY is still unverified. A full investigation (namespaces, nodes, pods, logs) ran through the gateway on 2026-11-20. Management traffic is untouched: SpokeCluster.spec.apiServer is not repointed.

Renewal: pause, replace, resume

The adapter parks the A2A task in auth-required; MAS asks ACME for a fresh A on the same task. The fresh A becomes a fresh H at the hub gateway and a fresh R in the adapter. Seen live: "task paused for credential renewal", then "renewed run credential" five seconds later.

Stage 2

MAS forwards Token A — azp never changes

MAS validates Token A against its issuer allow-list and principal allow-list, seals it (Fernet, Vault mao-run-credentials) into the task, and routes the question through its blueprint graph. The "Hub Cluster Investigator" node's bearer_token is empty, so MAS forwards Token A untouched to the Praxis hub gateway. Because forwarding does not change azp, the hub gateway's caller allow-list keeps admitting ACME's client identity, not MAS's. The stream to the hub is capped at 1200 s to fit an investigation.

How an A2A task becomes a MAS / Temporal workflow

A2A is the client-facing protocol. Temporal runs the workflow behind it; it is not another agent or a proxy in the request path.

    TS->>W: run parent lifecycle and child GraphTraversalWorkflow
    TS->>W: execute_graph_node activity for selected blueprint node
    W->>OUT: node delegates via A2A with current Token A
    OUT-->>W: separate downstream task ID, status, result
    W-->>TS: node activity result, continue graph
    W->>DB: persist session lifecycle / final output
    IN->>DB: project session + pending mailbox state into A2A task
    IN-->>A: task status / result via response, polling or stream

One conversation is not one workflow forever. A2A contextId identifies a conversation mapped to a MAS session. Each accepted new turn has its own A2A taskId and parent Temporal workflow ID a2a-<taskId>. The parent owns begin/complete/fail/cancel, and its child <parent>-graph traverses the blueprint. Graph nodes execute as worker activities, including calls to other A2A agents. A downstream task has a different task ID; the hub adapter will also bind it to an AgenticRun UID and execution step.

The state is deliberately split. Mongo stores task ownership, context→session mapping, outputs and renewal mailboxes; Temporal stores workflow event history; Redis carries live events/streams. MAS maps session state/output to A2A task status/artifacts, with pending approval → INPUT_REQUIRED and pending credential renewal → AUTH_REQUIRED. The latter can be shown while the underlying session/workflow is still running. Only sealed credential envelopes, never plaintext bearer tokens, should enter persisted workflow inputs.

Source evidence: MAS revision a6674f23f9d0, adapters/inbound/a2a/orchestrator.py, lib/mas/session/service.py, adapters/outbound/temporal/session_engine.py, and adapters/inbound/temporal/workflows/. Dispatch persists the handle before starting Temporal, uses REJECT_DUPLICATE, and retries an uncertain start with the same handle. This is source inspection, not a new live Temporal test.

MAS today: wait inside the worker, then continue

Before each graph node, WorkerCredentialResolver selects the newest usable session token or asks for renewal (default minimum validity: 60 seconds). A downstream 401/auth-required can trigger the same callback. The worker waits on the Mongo mailbox inside its existing activity, with Temporal heartbeats continuing. The inbound adapter accepts ACME's follow-up into that mailbox; it does not start a new workflow or send a Temporal signal. The wait returns, the A2A provider updates Authorization, and the activity continues. Completed Agent A is not intentionally called again while Agent B waits for credentials. Renewal is bounded, not an infinite wait.

401 and AUTH_REQUIRED are different. For a known authentication rejection before request acceptance, resend the original request with fresh credentials. If a downstream task already exists in AUTH_REQUIRED, send a credential-only follow-up with that task/context and a new message ID. A closed stream is reopened for the same task; it is not a new task. A normal 403 means insufficient permission, not a reason to keep renewing.

OLS fork (historical, removed): re-enter the same task before starting the query

In inspected OLS fork revision c46e88a4edc5, a rejected caller token at the MCP exchange sets AUTH_REQUIRED and returns before _run_query(). The follow-up's Authorization is validated for the same caller; _is_auth_resume() detects the paused task, and _original_request() recovers the investigation text/mode from task history. It re-runs request preparation and the exchange, then starts the ordinary OLS query using the existing task/context and conversation mapping. The renewal message is not a new question.

Important limit: this is a retry of the pre-query credential gate, not a saved Python stack or arbitrary tool checkpoint. The task store is process-local and the renewal window is bounded. The inspected query-pipeline error paths fail the task; they do not implement generic mid-query token renewal or durable resume after loss of the OLS process.

Hub (as implemented): the adapter's auth-required, then a fresh R

Implemented shape: the adapter keeps task → AgenticRun binding in its store, parks the task in auth-required, and on the follow-up exchanges the fresh H for a fresh R written to the same Secret (see "Renewal" above). The paragraphs below are the original plan for mid-command pauses; the sandbox-side command gate is not implemented, because R's 30 minutes covers a typical investigation.

Original plan: a durable run binding and an explicit step/command gate

The adapter must persist downstream task → AgenticRun UID → step/attempt, with the authenticated principal and immutable target. An execution wrapper must catch a credential-specific refusal and report a pending operation to the adapter; a bare oc process exiting with 401 cannot pause an A2A task on its own. The adapter exposes auth-required, MAS/ACME renew, and the resumed inbound call passes through Praxis for fresh H plus protected A. The adapter updates only that run's credential source and releases its credential gate. The wrapper reloads/reconnects and retries the denied operation; the spoke-facing PPE exchanges fresh A for fresh U.

Do not create another AgenticRun or repeat approved/completed steps. Keep the existing pod where possible. Upstream credential-pause conditions and wakeup mechanics still need implementation/verification; no existing CRD field is assumed. If the pod has already exited, a controlled new attempt needs an explicit checkpoint and safe operation boundaries, or the task must fail visibly and request a decision. Fresh credentials are not approval, and cannot revive a cancelled/terminal task.

Renewal is not exactly-once execution

Temporal replay can reuse recorded activity results, but a worker crash can retry an in-flight activity. Likewise, a command may have changed the cluster before its response was lost. Only a known pre-dispatch auth rejection is straightforward to retry. Writes, interrupted exec and ambiguous network outcomes require idempotency keys/preconditions, read-after-write reconciliation or human review—not replay of the entire graph. Renewal waits, heartbeats and activity/workflow timeouts must be compatible.

Evidence and tests: MAS's scripted integration test tests/integration/a2a/test_credential_renewal_flow.py exercises the real mailbox/resolver/A2A path with a simulated downstream, including reuse by later nodes. It is not a live Temporal+OLS deployment test. New hub acceptance tests must additionally prove same task/run IDs across renewal, no duplicate Agent A, safe restart recovery, unchanged approvals, wrong-owner rejection, deadline handling and no blind replay of ambiguous writes.

Stage 3 · Phase 1

The Praxis hub gateway exchanges A for H

The praxis-proxy Deployment is the hub gateway (a2aUpstream.exchangeAtPraxis). It validates Token A (RS256 via the issuer's JWKS, audience mas-a2a, claim.azp allow-list), then runs delegate(hub-delegator, target: hub-adapter, audience: lightspeed-hub-a2a) as confidential client mas-a2a and forwards Token H to its single upstream, the adapter. H carries the hub audience and the audience-scoped role group the hub's RBAC binds.

No protected-A handoff. The plan required Praxis to forward A on a side channel so the run could use it later. That is unnecessary now: the run credential R is derived from H in the adapter, so A stops at the hub gateway.

Agent card passthrough. The card at /.well-known/agent-card.json and /a2a/.well-known/agent-card.json is the adapter's own, routed unauthenticated. A static card with protocolVersion 1.0 made MAS call v1 method names the adapter does not serve; the adapter's card says 0.3, so MAS uses message/stream.

Stage 4 · Phase 1

The adapter creates the AgenticRun as the caller, then mints R

The adapter is a net-new Go service in lightspeed-hub (a2a-adapter/, flags --inbound-hub-token and --run-token-audience). It serves the A2A endpoint and agent card, creates the AgenticRun with Token H — the hub API records the caller as creator — and watches the run with its own ServiceAccount to return task status. Requester × target is enforced by a ValidatingAdmissionPolicy (CEL) shipped in charts/all/lightspeed-hub, not a webhook.

It then exchanges H as client lightspeed-hub-a2a for the run token R and stores it in ls-run-token-<uid> (key token-a, the operator's contract name). Tokens never go into the CR.

Phase 1 · superseded Stage 5

The stock spoke credentials are not used in gateway mode

The plan's Phase 1 kept the hub's stock spoke access: a per-run ServiceAccount on the spoke, provisioned through the standing kubeconfig, with a 24 h TokenRequest token in the sandbox. The deployment went straight to gateway credential mode instead, so in this pattern the operator creates no spoke ServiceAccount, no spoke-management kubeconfig and no approved execution RBAC. The stock path still exists in the operator for clusters not using gateway mode.

Gateway mode (lightspeed-agentic-operator configuration):
  sandbox kubeconfig  → spoke gateway Service, tokenFile = R
  spokeManagementAccess → nil (no spoke-kubeconfig-<spoke> needed)
  ensureSA            → skipped; serviceAccount = ""
Stock mode (not used here):
  spoke sees system:serviceaccount:openshift-lightspeed-managed:ls-<step>-<runUID>
Phase 2 Stage 6

The spoke gateway mints U per call (option B1, implemented)

The constraint every option shared: the spoke must see a token that speaks for the requester, which only an RFC 8693 exchange produces, and the requester's credential must cross the gap between the request and a sandbox that may start much later.

What was chosen. Option B1 — a Praxis instance in front of each spoke API exchanging per call — is what runs. The proxy spike passed, so option A (the adapter brokering U into a Secret, with a refresh loop) was never built; option B2 (the sandbox exchanging for itself) stayed rejected.

What changed from the plan. The plan parked the caller's Token A for the sandbox. The implementation parks R instead: minted from H by the adapter, 1800 s, audience praxis-spoke-gateway only. The sandbox holds R; the gateway holds the exchanger's client secret; no SVID in the sandbox. Because R's azp is lightspeed-hub-a2a (the exchanger), that is what the spoke gateways allow-list — inheriting the hub gateway's acme-agent caused a 403 on every call until fixed.

Phase 2 Stage 7

The spoke applies the caller's audience-scoped RBAC

The spoke's Authentication/cluster (OpenShift Native OIDC) trusts the hub Keycloak with the spoke's audience and maps sub → keycloak:<sub>, groups → keycloak:<group>. U's group praxis-spoke-<id>:reader is bound to cluster-reader and cluster-monitoring-view (charts/all/lightspeed-hub spokeReaderRBAC). The agent can never exceed what that role grants, and approval gates whether a run proceeds, not how much it may do. Live, the hub is its own spoke (praxis-spoke-hub).

Phase 3 · not started Stage 8

Registration becomes "URL + trust"

Status: not started. In gateway mode the operator no longer uses spoke management at all, so what remains is the lightspeed-hub operator's own registration and health traffic. Phase 2 still leaves the standing kubeconfig for those control-plane duties (registration checks, health probes, provisioning). Phase 3 replaces it with an oidc implementation of the hub's CredentialSource: the hub operator mints a token for its own service identity and presents it to spoke API servers, backed by a one-time minimal probe ClusterRole. No credential is ever handed over. This is more than one interface — CRD validation, controller wiring, refresh-aware transports and the provisioning path all change — so it is scoped as its own small project.

Who mints, who renews

No refresh tokens: ACME re-authenticates for a fresh A, and every other token is re-derived from it. An exchanged token takes the exchanging client's access.token.lifespan, even past the subject token's expiry (verified live), which is why R can outlive A and H.

Open items

  • The caller is still an agent identity. Human login in ACME remains a TODO.
  • Renewal past one R. Steps longer than 30 minutes, especially behind long approvals, need the auth-required loop exercised end to end.
  • Per-spoke R. One R works at every spoke gateway; binding R to its target spoke would stop cross-spoke replay.
  • SSO callers. The hub gateway's delegator sends no subject_issuer, so an SSO-issued A cannot be exchanged.
  • Target header from code. MAS should inject X-Hub-Cluster deterministically rather than rely on the model.
  • Sandbox egress. Default-deny egress for sandbox pods (only the gateway, DNS, LLM and hub-result paths).
  • kubectl exec through the gateway (SPDY) is unverified; large unbounded log reads hit the 32 MiB ceiling.
  • Existing MAS management Route exposure (route.enabled: true + providerMode: dev) should be fixed independently.
