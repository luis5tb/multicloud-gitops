Agentic pattern: investigations, Ask Red Hat and partner agents

ACME asks the hub-hosted MAS orchestrator with one local token, Token A, for every destination. MAS forwards that same Token A to whichever agent it delegates to, always through a Praxis instance. The hub gateway exchanges it inside Keycloak for cluster investigations. The egress gateways (one per external agent) trade it for a token from that agent's own identity provider, minted with the gateway's own client. Red Hat SSO fronts Ask Red Hat, and a partner IdP fronts a partner agent. No external token ever enters Keycloak, and nothing external is stored in MAS. The investigation token walkthrough is in agentic-e2e-token-flow.html.

Three kinds of destination, one caller token. Investigations go through the hub gateway and exchange Token A inside Keycloak (A → H → R → U, the same sub all the way). External agents go through their own egress gateway, which never exchanges Token A. It authenticates it, then mints a separate token at that agent's IdP with the gateway's own client. Steps ⑩ ⑪ ⑫ are the Ask Red Hat path; the partner path is identical with its own IdP, client and card.

External agents through egress gateways

What an egress gateway does

  • Validates Token A against the local Keycloak only, and enforces the azp allow-list
  • Serves the agent's A2A card from its configuration, with the card's URL rewritten to itself (the a2a-sdk sends to the card's URL, so this keeps MAS on the gateway)
  • Mints a token at the agent's IdP with client_credentials as its own client, and replaces the outbound Authorization
  • Forwards to one fixed A2A endpoint, with Host set to that endpoint

Identity: one account, not users

The agent sees the gateway's client account for every MAS user and every request.

  • Its permissions apply to everyone the gateway's allow-list admits
  • Quotas and the agent's audit log see that one account; which user asked is in ACME's and MAS's records
  • Right for shared knowledge (Ask Red Hat); wrong where the agent must enforce a user's own entitlements

Configuration

  • Card: variants/standalone/praxis-egress-<key>-card.yaml
  • Endpoint, IdP, Vault record: …-stage.yaml or …-production.yaml
  • Credentials: one Vault record per environment with client-id and client-secret; nothing credential-related in git
  • MAS: an a2a_agent_node with base_url = the gateway; no token, no stored card

Ask Red Hat: switching stage → production

MAS never changes: its Ask Red Hat node points at https://praxis-egress-ask-red-hat.praxis-proxy.svc:8443/api/ask/v1/a2a in both environments, and the card is shared (the stage and production cards were identical apart from url, which the gateway replaces). Only the gateway's environment file changes.

  3. Swap the file: in variants/standalone/values-standalone.yaml, under the praxis-proxy app's extraValueFiles, replace /variants/standalone/praxis-egress-ask-red-hat-stage.yaml with /variants/standalone/praxis-egress-ask-red-hat-production.yaml. Commit and sync; the gateway rolls automatically.
  4. Check: the gateway's ConfigMap shows access.redhat.com:443, the pod's render-config init container exited 0, and ACME answers a Red Hat question. To go back, swap the file again.

Credentials are read at pod start. If only the Vault record changes (rotation), restart the gateway once the ExternalSecret has synced: oc -n praxis-proxy rollout restart deploy/praxis-egress-ask-red-hat. The value files are loaded with ignoreMissingValueFiles, so a mistyped path silently removes the gateway; a chart test guards the committed paths.

Components

ACME agent

Chat agent (ns acme-agent). Answers Red Hat questions by delegating to MAS.

  • Keycloak client acme-agent, authenticated with its SPIFFE JWT-SVID (no static secret)
  • Calls MAS A2A with Token A for every kind of question
  • LLM through LiteLLM

MAS (mao)

Multi-agent orchestrator on the hub cluster; the A2A endpoint is the pattern's front door.

  • MAS A2A validates Token A and seals it (Fernet) into the Temporal task
  • mas-worker forwards that one credential to the chosen node: the hub gateway or an egress gateway
  • mas-worker and mas-api trust the OpenShift service CA (identity.serviceCaTrust) for the internal egress gateways

Praxis hub gateway

praxis-proxy Deployment and Route (ns praxis-proxy).

  • Validates A, azp allow-list
  • RFC 8693 delegation as mas-a2a: A → H
  • Routes A2A to the adapter; passes the adapter's own agent card through

Praxis egress gateways

One per external agent: praxis-egress-<key> (chart value egressGateways).

  • Internal TLS Service (service-serving cert, :8443), no Route; NetworkPolicy admits mas-worker and mas-api only
  • Serve the agent card from config; mint with subject: this_workload; forward to one fixed endpoint
  • Credentials: one ExternalSecret from the environment's Vault record (client ID via init container)

Ask Red Hat agent (external)

Red Hat's hosted knowledge agent, behind Red Hat SSO.

  • Reached only through praxis-egress-ask-red-hat
  • Receives token S (the SSO client's account), never Token A
  • Stage and production differ only in endpoint, token endpoint and Vault record

Partner agent (example)

Any external A2A agent behind any OAuth 2.0 IdP with client_credentials.

  • Its own egress gateway, client, Vault record and card
  • Receives token P (the partner client's account)
  • How to add one: docs/ADDING_AN_EXTERNAL_AGENT.md

lightspeed-hub A2A adapter

Translates A2A tasks into AgenticRuns (repo lightspeed-hub).

  • Creates the AgenticRun with H (the caller's identity)
  • Exchanges H → R as lightspeed-hub-a2a; stores R in ls-run-token-<uid>
  • Watches runs with its own ServiceAccount; renewal via A2A auth-required

lightspeed-agentic-operator

Runs the investigation (gateway credential mode).

  • Agent default, LLMProvider vertex, ApprovalPolicy cluster
  • Sandbox kubeconfig points at the spoke gateway, token = R
  • No spoke ServiceAccount, no spoke-management kubeconfig

Praxis spoke gateway

One per spoke: praxis-spoke-<id> (here praxis-spoke-hub).

  • Validates R (aud praxis-spoke-gateway, azp lightspeed-hub-a2a)
  • Per call, exchanges R → U as praxis-spoke-gateway
  • Fixed upstream: the spoke API, TLS verified; IPv4-only DNS sidecar

Keycloak (RHBK)

Realm rca, imported by charts/all/keycloak-oidc.

  • Issues A; performs the three internal exchanges
  • Never sees an external token on these paths
  • Issuer for OpenShift Native OIDC on the kube APIs

Kube APIs

OpenShift Native OIDC maps sub → keycloak:<sub>, groups → keycloak:<group>.

  • Hub: H's group may create AgenticRuns (plus a ValidatingAdmissionPolicy on the target)
  • Spoke: U's group gets cluster-reader and cluster-monitoring-view
  • A and R are rejected (401)

Vault, ESO, external IdPs, Vertex

Supporting services.

  • Vault + External Secrets deliver every client credential, including one record per external agent and environment
  • Red Hat SSO and partner IdPs: used only by their egress gateway
  • Vertex AI: one credential and model for MAS and the sandbox
