# Greenfield ACME → Praxis → OpenShift Lightspeed plan

**Status:** source-level implementation is in progress; no live cluster validation or production image/catalog publication has occurred. The former RCA source/chart and standalone Pattern app have been removed for this greenfield target.
**Scope:** greenfield `standalone` deployments only. This is not an in-place migration procedure for a cluster running the former RCA agent. The `hub` and `group-one` variants do not deploy the ACME/Lightspeed chain.

## Outcome and boundaries

The request path must be **`acme-agent → Praxis → target cluster's OpenShift Lightspeed → that cluster's OpenShift MCP → OpenShift API`**. ACME stays the A2A coordinator; Praxis stays the public, Keycloak-validating authorization gateway and selects a **configured** Lightspeed backend from an ACME-supplied `X-OLS-Cluster` header. ACME's own lightweight coordinator model is set to OpenAI-compatible LiteLLM model `openai/gpt-6-luna`; this is separate from Lightspeed's investigation model. A locally maintained copy of [openshift/lightspeed-service](https://github.com/openshift/lightspeed-service) supplies the Lightspeed service, extended to speak A2A to ACME. Lightspeed uses the existing Gemini-on-Vertex choice (`vertex-google`, `gemini-3.8-flash`, Google project `redhat-marketplace-dev`, location `global`) for its own reasoning, instead of creating an `AgenticRun` for another component to reason on its behalf.

**Correction after reviewing the OpenShift Lightspeed Operator:** `lightspeed-service` is an MCP *client*, but the separate [openshift/lightspeed-operator](https://github.com/openshift/lightspeed-operator) **does automatically deploy an OpenShift MCP server** and configure the service to use it. Its `OLSConfig.spec.ols.introspectionEnabled` defaults to `true` when omitted; setting it to `false` removes the operator-managed MCP resources. Use the operator-managed MCP deployment rather than packaging a duplicate server in our own Helm chart. Merely running `lightspeed-service` with an `mcp_servers` YAML entry, *without the operator*, would still require a separately deployed server. The prior version of this plan conflated those two deployment modes.

Preserve the security properties of the current deployment: SPIFFE-bound Keycloak clients, independently validated inbound caller tokens, Praxis's allow-list, per-request RFC 8693 exchange to an `openshift-mcp` audience, MCP bearer passthrough, OpenShift OIDC/RBAC enforcement, verified TLS, and no public route/bypass to the Lightspeed service or MCP backend. **Never substitute a pod ServiceAccount token, a shared static MCP token, or `dev_config.disable_auth` for the caller's delegated identity.**

## Cluster selection and future multi-cluster routing

**User contract.** Update `agents/acme_agent/src/acme_agent/agent.py`'s system instruction to request the **target OpenShift cluster API URL** (for example `https://api.bm-cluster.e2e.bos.redhat.com:6443`) and ask a clarifying question if it is absent or ambiguous. Never infer a cluster from a resource name, pick a silent default, or begin an MCP investigation before the target is resolved. A prompt alone cannot enforce this: add a deterministic pre-dispatch validator in ACME that extracts one explicit URL from the request or structured conversation state, validates it against a GitOps-managed registry of allowed clusters, and either produces exactly one selected cluster ID or rejects/asks again. The current `agents/acme_agent/src/acme_agent/ui.py` sends one-shot A2A requests without carrying a conversation/context ID into the next request; until that is changed, require the URL on **each** message rather than assuming a clarification reply can recover prior state. Optionally add a required, validated cluster-URL control to that UI while still validating A2A requests arriving from other clients server-side. If the URL changes mid-conversation after stateful support is added, make the user confirm a new target; do not reuse the previous cluster implicitly. Model output must not invent a URL or header.

**Stable routing key, not a free-form destination.** Canonicalize the API URL (`https` only; lowercase/IDNA-normalized host; explicit effective port; no credentials, path, query, fragment or ambiguous redirects), then derive a DNS-safe cluster ID from the host and port: lowercase, replace separators with `-`, and, if necessary for a 63-character cap or a collision, append a short stable SHA-256 suffix of the **canonical URL** after truncation. For the single currently configured cluster, `https://api.bm-cluster.e2e.bos.redhat.com:6443` maps to **`api-bm-cluster-e2e-bos-redhat-com-6443`**. Configure the exact URL → ID → upstream mapping in the pattern's cluster registry; verify it on the real cluster (`oc whoami --show-server`) before treating this example as authoritative. Send the ID, **not** the URL, as `X-OLS-Cluster: api-bm-cluster-e2e-bos-redhat-com-6443` on the authenticated A2A RPC to Praxis. Reject unknown URLs/IDs or multiple/conflicting values; never construct a network destination from untrusted header content. Separate display names from routing IDs so renaming a friendly label cannot silently retarget traffic.

**ACME transport change.** Today `agents/acme_agent/src/acme_agent/agent.py` creates `RemoteA2aAgent` children with one shared `httpx.AsyncClient`; its only request hook (`agents/acme_agent/src/acme_agent/auth.py`) attaches the Keycloak bearer, not a cluster header. Add per-invocation target selection and propagate the selected ID through a request/task-scoped context into **every** downstream A2A HTTP RPC, including polling, cancellation and context follow-ups. Avoid a process-global mutable variable or a permanent default header on the shared client: concurrent ACME conversations must not swap clusters. If ADK's `RemoteA2aAgent` cannot reliably carry an invocation-scoped header through all callbacks, implement a narrow A2A transport adapter rather than rely on a prompt or mutate shared client headers. The current ACME public endpoint is one-shot and has no durable task/context-to-target store: initially require the URL on every inbound `message/send` and reject inbound `tasks/get`, cancel or streaming methods rather than allow an unpinned follow-up; implement authenticated durable affinity before claiming those methods. The public agent card is fetched independently of the user's request and must remain discoverable before cluster selection; serve a cluster-neutral card via Praxis advertising the **single public Praxis HTTPS RPC origin**, with capabilities compatible across backends. Alternatively, implement authenticated, target-scoped card discovery, but do not let untrusted card metadata redirect ACME around Praxis. Keep Keycloak auth and TLS verification on the actual RPC.

**Praxis routing/authorization and version upgrade.** Praxis Core v0.7.2 is a pre-release and is a separate version line from Praxis AI. The tracked `vendor/praxis-ai` v0.4.1 source snapshot now locks Core crates to 0.7.2 and includes the fail-closed `ols_cluster_guard`. Focused guard tests, all 1,436 filter tests, both integration tests, proxy build, docs/example checks, and a local container build passed; the local image validates the guard example. This is not a published or scanned deployment artifact. The chart is disabled by default, has no legacy/RCA upstream, and requires a guard-enabled non-stock digest plus a non-empty static registry when enabled. Remaining work: pin builder/runtime base images by digest, complete runtime duplicate-header and HTTPS/SNI/CA tests against the actual candidate container, generate/scan an SBOM, publish the image, and record its registry digest/provenance. Do not set a Core version as the AI image version. The only anonymous application route is the exact public agent-card GET; JWT authorization precedes target selection and the guard rejects missing, duplicate, malformed, or unknown selectors before the router.

**Multi-cluster session safety.** All A2A task/context operations must return to the **same target cluster** selected for their initial `message/send`; pin the selected ID to task/context and deny a later request whose header conflicts with the owner. Praxis AI 0.4.1 includes optional A2A task-owner routing, but its example uses an in-memory store unsuitable for multi-replica gateway deployments; decide whether to use a persistent task-owner store or rely on ACME's tested per-task target propagation, and fail closed on mismatch/unknown owner rather than silently selecting another cluster. When future OLS installations live on other OpenShift clusters, provision trusted private/controlled TLS connectivity to each fixed backend, its serving CA/SNI in Praxis's upstream TLS settings, network isolation and the required Keycloak/SPIFFE trust in **each** cluster. Do not expose an unprotected direct OLS Route as a shortcut, assume `svc.cluster.local` resolves cross-cluster, or assume one cluster's OIDC/RBAC grants automatically apply to another; the chosen backend must access its **own** operator-managed MCP and OpenShift API, and the target cluster must independently validate Token B and grant the mapped group only its local rights. A single federated Keycloak client currently matches one SPIFFE workload subject; adding cluster workloads will require a per-cluster client/subject plan and ACME subject-token audience mappers. Before adding the second cluster, evaluate distinct **MCP token audiences per cluster** (and per-cluster OpenShift trusted-audience configuration) so a Token B minted for cluster A cannot be replayed against cluster B merely because both trust the same Keycloak realm and group. Test wrong-backend behavior (a backend should reject a mismatched cluster ID) and cross-cluster token replay before adding a second cluster.

## Keycloak tokens, Lightspeed/MCP authentication and OpenShift RBAC

**Two different tokens, two different checks.** The browser request to ACME is currently attributable to ACME's **service account**, not to a human user. ACME obtains Token A from Keycloak using its SPIFFE JWT-SVID (`client_credentials` with the `jwt-spiffe` client assertion). Praxis verifies Token A's signature, issuer and audience, then checks the standard Keycloak `azp` claim through `role: user` and an explicit `deny(...)` APL action; the new Lightspeed A2A endpoint independently requires `azp=acme-agent`. Token A needs an inbound audience such as `lightspeed-a2a` **and** the real `lightspeed-mcp` client audience for Keycloak's exchange. Do not assume that a token with only those audiences will pass Lightspeed's stock Kubernetes `TokenReview`: OpenShift's API server trusts only the configured audiences. The recommended A2A path validates Token A locally against Keycloak rather than broadening OpenShift's trusted audiences solely to make Token A usable as an API token. Keep the stock Lightspeed `/v1/query` and other REST paths on `k8s` auth (`TokenReview` plus `/ols-access` `SubjectAccessReview`), with no ACME `/ols-access` grant unless a separately reviewed direct-REST use case needs it; **no `noop`/`disableAuth` workaround**. The A2A adapter must bind its validated caller to an isolated Lightspeed conversation/task identity and run the usual query pipeline, but supply Token B—not A—to the generated MCP client's `Authorization: kubernetes` resolver.

**How Token B is issued.** Configure the Keycloak realm with a new SPIFFE-federated confidential `lightspeed-mcp` client: `clientAuthenticatorType: federated-jwt`, `jwt.credential.issuer: spiffe`, and `jwt.credential.sub: spiffe://<trust-domain>/ns/openshift-lightspeed/sa/<actual operator-created app-server SA>`. Confirm that SA name from the chosen operator release rather than guessing it. Its attributes need `standard.token.exchange.enabled: "true"` and a mapper adding the **real** `openshift-mcp` audience client (`included.client.audience`). ACME's client needs an audience mapper for `lightspeed-mcp` as well as a *separate* custom mapper for the A2A inbound audience. Request the JWT-SVID with the **Keycloak realm issuer URL** as its assertion audience; submit it with `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-spiffe`, the original access token as `subject_token`, and `audience=openshift-mcp` to Keycloak's token endpoint. Omit the `client_id` form parameter, as the existing SPIFFE-federated flow requires. Put a `groups` mapper on both ACME and the exchanging client and ensure ACME's Keycloak service account really belongs to `acme-agent-lightspeed` (or a deliberately migrated group). Confirm from a **live** exchange that Token B has the expected Keycloak `iss`, `aud=openshift-mcp`, `azp=lightspeed-mcp`, the same `sub` as Token A, and `groups: ["acme-agent-lightspeed"]`; do not assume exchange automatically preserves groups. Do not expose Token A to MCP, share Token B across requests, or use the Lightspeed/MCP pod ServiceAccount as Token B's subject. Keycloak's standard exchange does not supply an `act` claim here, so audit the actor via `azp`/A2A logs separately.

**What OpenShift must trust and map.** The pattern's `charts/all/keycloak-oidc/templates/openshift-authentication.yaml` creates `Authentication/cluster` with `spec.type: OIDC`; `spec.oidcProviders[].issuer.issuerURL` must equal Token B's `iss`, and `issuerCertificateAuthority.name` must point to the synced Keycloak CA ConfigMap in `openshift-config`. Keep `openshift-mcp` in `spec.oidcProviders[].issuer.audiences` via `openshiftOIDC.extraAudiences`; the requested token-exchange audience and this API-server audience **must match**. The chart maps JWT `sub` to an OpenShift username prefixed `keycloak:` and `groups` to groups prefixed `keycloak:` (`openshiftOIDC.usernameClaim/usernamePrefix/groupsClaim/groupsPrefix`). Hence Token B should authenticate as `keycloak:<Token A sub>` in group `keycloak:acme-agent-lightspeed`; Kubernetes RoleBindings refer to that **prefixed group** and need no pre-created OpenShift User/Group object. Keep the prefix to prevent collisions with reserved `system:` groups. API-server verification of signature, issuer, audience and expiration precedes RBAC; RBAC is evaluated against **Token B's** mapped identity, not `azp` or the MCP SA. Native OIDC is cluster-wide and remains disabled in the greenfield standalone values until its preflight passes; retain break-glass access and test audience/mapping changes before enabling it.

**Operator-managed MCP security.** The downstream operator source now configures required OAuth, independent Keycloak issuer/audience validation with a mounted CA, bearer passthrough, read-only behavior, restricted toolsets/resources, and no pod-ServiceAccount fallback. The service passes only the per-request exchanged Token B to the built-in `openshift` MCP client; other configured MCP endpoints are excluded from A2A tool resolution. Unit tests and operator `make test` cover the source changes, including CA validation/rotation behavior. These changes are not available in a released operator image/catalog: the checked-in bundle still identifies as 1.1.4 and must not be published under that version. The old standalone `charts/all/openshift-mcp-server` chart/application has been removed from this Pattern; do not recreate a second MCP server beside the operator-owned one. NetworkPolicies are additive; inspect the operator-generated rules plus the explicit Praxis-to-OLS allowance on the target CNI before deployment.

**Rights to grant (and not grant).** Add namespace-scoped `Role`/`RoleBinding` resources for the mapped `keycloak:acme-agent-lightspeed` group in precisely the namespaces and read resources needed for investigation; the exact verbs/subresources depend on the reviewed MCP tools. No automatic `view`/cluster-admin ClusterRoleBinding, no Secret or RBAC object access, no create/patch/delete by default. **Read-only does not mean data-safe:** Kubernetes Pod objects can contain literal environment values, annotations, or command arguments, and pod logs can contain credentials; the operator's Secret/RBAC deny-list does not remove those values from pod specs or log output. Grant `get/list` on pods or `get` on logs only after assessing real workloads and the exact tool response; prefer a reviewed server-side allow-list/redaction if raw objects could expose secrets. OCP RBAC is the final, authoritative allow/deny for each Kubernetes API call; the MCP server's denied-resource list and tool hints are supplemental. The existing `agenticRun.namespaceAllowlist` admission policy controls **only** AgenticRun creates, not MCP reads. Cluster-scoped queries or observability APIs require separately reviewed grants; test that an all-namespaces request cannot infer data outside ACME's authorized scope. If the intended caller later becomes a human user rather than ACME, this design must change to propagate the human subject/group claims through Keycloak; ACME's current client-credentials grant cannot impersonate a human.

For example, **only if** pod listing in `payments` is in scope, the resulting RBAC could start as follows (add each required resource/namespace deliberately; do not automatically grant pod logs, which can contain secrets):

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: lightspeed-mcp-investigate
  namespace: payments
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: lightspeed-mcp-investigate
  namespace: payments
subjects:
  - kind: Group
    name: keycloak:acme-agent-lightspeed
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: lightspeed-mcp-investigate
  apiGroup: rbac.authorization.k8s.io
```

**Verification matrix.** Obtain Token A and Token B on a test cluster; decode **claims only** (never record raw bearer values). Use a TokenReview or a harmless real API call with B to verify `authenticated`, username and groups, and `oc auth can-i --as=<mapped-username> --as-group=keycloak:acme-agent-lightspeed ...` to pre-check RBAC (impersonation is *not* a replacement for the real-token test). Check allowed reads, denied namespaces, forbidden writes, wrong/expired issuer/audience, absent group mapper and a direct MCP call without a bearer. Confirm the MCP server returns `401` for missing bearer, `401` (with local OIDC enabled) or API-server denial for invalid bearer, and never succeeds using its pod SA. Observe API audit logs to prove the OpenShift username/group, not the Lightspeed/MCP SA, authorized the requests. Test OIDC CA/key rotation and the operator's reconciliation of all hardening config.

## Acceptance checks and rollout gates

- **Source/build:** pinned imported revision and license, reproducible service image, tested operator `--service-image` override across reconcile/upgrade, and a pinned Praxis AI image/digest demonstrably built against Praxis Core v0.7.2 (record Core and AI versions separately; the Core tag is pre-release). No credentials committed; chart `helm lint`/`helm template` both standalone and with `values-global.yaml` + standalone values; valid `OLSConfig` and secret references. Verify Gemini project/location/model, `MCPServerReady`, operator-managed MCP Deployment/Service, and generated `openshift` entry in effective `mcp_servers`.
- **A2A/transport:** ACME can discover a card advertising the public Praxis HTTPS URL and complete a real A2A request; tasks and errors propagate correctly, including timeout/retry and concurrent sessions. Only the card and explicitly chosen probe are anonymous; direct Lightspeed and MCP access (outside their permitted peers) is denied.
- **Cluster routing:** with the prompt and code, missing/ambiguous/unknown cluster URL asks for clarification or fails closed before a downstream call; the registered API URL maps to the documented `X-OLS-Cluster` value on every authenticated A2A RPC. Praxis JWT and cluster-header checks precede routing; header spoofing cannot create an arbitrary upstream. Test a missing, duplicate, malicious, unknown and mismatched header and the single valid header against the pinned Praxis binary. Exercise two simulated cluster backends with interleaved ACME conversations and A2A task polling to prove both routing isolation and no shared-client header leakage; exercise gateway task ownership/multi-replica behavior before adding a real second cluster.
- **Identity:** missing, expired, wrong-issuer, wrong-audience, wrong-client and malformed Token A fail at Praxis **and** at Lightspeed if Praxis is bypassed in a unit/integration test. Validate issuer TLS/CA rotation, SPIFFE subject, token-exchange failure behavior and no credential leakage in logs, traces, cache or A2A task output.
- **Authorization:** inspect real Token A/Token B claims (redacted); Token B keeps ACME's `sub`, has `azp=lightspeed-mcp`, `aud=openshift-mcp`, and the expected Keycloak group. Verify the actual API-server-mapped `keycloak:` username/group; OpenShift accepts B for permitted MCP reads and denies disallowed resources/namespaces and all writes by default. Verify MCP rejects a missing bearer without falling back to its ServiceAccount, and that no other static MCP credential can confer those permissions. Confirm the operator retains these properties after reconcile/upgrade.
- **Function:** OLS uses Gemini for tool-using analysis, can call the operator-managed OpenShift MCP backend with the exchanged token, and returns a grounded answer through Praxis to ACME. Test invalid/absent Vertex credentials and MCP failure: no fallback to another model, anonymous tools or a falsely successful answer. Plain OLS answers do not claim compatibility with the former RCA `AnalysisResult`/remediation-proposal workflow; any need for that output contract requires a separate product design.
- **Greenfield activation:** verify the full path in a disposable/test cluster first, establish/verify cluster-admin break-glass access, then enable target-specific values and flags. If validation fails, disable ACME delegation, Praxis routing, and OLS A2A/introspection together; do not introduce an RCA fallback, use broad RBAC, or disable token validation to troubleshoot.
